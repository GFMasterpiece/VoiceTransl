# 文件夹音频批处理

状态：Implemented。已实现“工作流模板＋批次＋逐文件运行”，通过自动化回归与 Windows Edge 全栈验收。

## 目标与范围

在同一项目内添加一个或多个文件夹中的音频，用同一份已保存工作流逐文件运行。每个音频保留独立运行、节点记录及产物，批次统一管理清单、调度、进度、取消、失败重试和打包下载。批处理不要求增加音频输入节点，不合并时间轴。

首版包含文件夹/多文件导入、可选递归、上传预检与逐项源语言、项目已有资源选择、服务端持久队列、有界并发、分页记录、失败隔离和结果 ZIP。当前仍只有音频直通与 Mock；不恢复真实 Provider、五阶段流程、目录监听、自动增量处理、混音、子工作流或任意节点续跑。

## 用户流程

1. 打开画布工具栏的批处理面板，可重复添加文件夹或选择多份文件；多个目录各有独立来源标识，同名资源不覆盖。
2. 按服务端上传策略校验扩展名和大小，显示相对路径、大小、状态及源语言，允许排除文件和修正语言；不猜测源语言。上传与运行分开，上传失败保留成功资源，重试不再次上传成功项。
3. 可选择已上传到项目的资源。启动前必须保存有效图，音频资源输入使用运行上下文，不显式绑定固定音频。面板解释未保存、固定绑定等阻塞原因，不自动修改图。
4. 确认音频清单后提交一次批次；服务端固定工作流和清单，并为每个文件创建独立运行。开始后允许编辑公共图，已排队项继续使用原批次快照。
5. 面板分页查看批次历史与逐文件状态，可取消活动批次、重试失败/中断项并下载结果。关闭面板或离开画布不取消服务端批次，重新打开从 REST 读取真实状态。

未上传的浏览器 File 只保存在当前项目编辑器会话，关闭面板保留；刷新后需要重新选择。导航和浏览器离开应保护待上传文件和上传中的请求。已上传资源、已提交批次及其结果由服务端持久化。

## 资源来源与当前文件信息

沿用原 multipart 追加资源 API，在 `file/source_language/name` 外增加可选的 `origin_root_id/origin_root_name/origin_relative_path`，三者全有或全无。新增可空 `SourceAsset.origin={root_id,root_name,relative_path}`；相对路径不含根目录名，basename 与上传文件名一致。校验安全来源 ID、目录显示名及跨平台相对路径，拒绝绝对路径、目录穿越及危险路径字符。来源仅为元数据，服务器实际存储仍按服务端生成的音频 ID 隔离。

`source_info`“当前文件信息”节点无输入、配置为 `{}`，输出 `filename/stem/source_language/relative_path/root_name` 五个字符串端口；作为显式参数根，不计入音频源数量。可将 `stem` 连接输出命名，将 `source_language` 连接需要语言的参数。旧资源没有来源时，相对路径使用原文件名、根目录名为空。新增节点和端口通过注册表发布，目录 shape 不变，保持 workflow capability schema `1.5`。

## 批次契约

接口均在 `/api/v1/projects/{pid}/batches` 下：

| 方法与后缀 | 契约 |
| --- | --- |
| `POST /` | `{workflow_revision,audio_ids,request_id}`；清单 1–10000 项，不允许重复；返回 202 批次摘要 |
| `GET /` | `limit/offset` 分页摘要；默认 20、最大 100 |
| `GET /{bid}` | 批次详情及固定的 `workflow` 快照，不内嵌完整项列表 |
| `GET /{bid}/items` | `limit/offset` 分页文件任务 |
| `POST /{bid}/cancel` | 停止派发并取消活动文件运行；终态幂等返回 |
| `POST /{bid}/retry` | `{request_id,include_cancelled:false}`；用原快照为 failed/interrupted 项创建新批次，可明确包含 cancelled |
| `GET /{bid}/download` | 安全 ZIP 和结构化结果清单 |

摘要包括批次 ID、项目 ID、状态、工作流版本、时间、取消标记、原批次 `retry_of`、总量、各项状态数量和安全错误。文件任务包括索引、音频 ID、原音频名、源语言、来源目录、状态、运行 ID、时间和错误。文件任务状态为 `queued/running/completed/partial/failed/cancelled/interrupted`；批次另有 `cancelling`。部分终端失败的单文件 `partial` 不冒充成功，默认失败重试不包含 partial。

新 `WorkflowRun.batch_id` 可空，标识批次子运行；普通运行和缺少字段的旧历史按原单运行解释。前端不能将重新打开的批次子运行误当作必须锁住公共画布/导航的单运行，也不能因项目另有批次就解除真正单运行的既有保护。

同项目首版只允许一个活动批次。相同 `request_id` 和相同有效载荷返回原批次；同 key 不同载荷返回 `BATCH_REQUEST_CONFLICT`。前端对不确定的网络结果保留 key 与载荷供重试，避免重复创建。固定资源绑定返回 `BATCH_EXPLICIT_AUDIO_BINDING`，项目已有活动批次返回 `BATCH_BUSY`；沿用 `AUDIO_BUSY`、`WORKFLOW_REVISION_CONFLICT` 等现有错误。

## 执行、取消与恢复

- 提交时一次性校验资源归属和图版本，冻结完整工作流、音频清单及源名称/语言/来源。执行从冻结快照创建新运行，不循环读取公共最新图。
- 全部排队项提前参与音频忙碌预留；单文件运行和批次共用同一忙碌边界及全局并发限制。排队、运行、取消清理期间不得删除项目。
- 服务端采用固定数量的工作任务调度清单，不为每个文件创建等待 semaphore 的异步任务；首版保持单进程、单 worker、文件系统持久化，不引入数据库或外部队列。
- 文件失败只影响该文件，其他文件继续。取消先停止派发、标记未开始项，再等待活动执行完成取消和资源清理，之后释放预留。
- 服务启动将未结束批次项标记中断，不自动重新发送请求。关闭服务先清理批次调度，再回收单文件执行；明确重试生成新批次及新运行，保留旧记录。
- 新增音频不进入已经提交的清单，修改公共图不影响该批次，重试沿用原批次图。若需要采用新图，应显式创建新批次。

## 结果与兼容边界

ZIP 按来源根、相对目录及稳定的文件任务标识隔离，同名根目录、同 stem 不同扩展和多个导出节点不能覆盖。`manifest.json` 包含 `format=voicetransl.batch-results`、`schema_version=1.0`，关联源文件、任务状态、运行、节点及结构化 artifact；缺失运行和文件分别记入 `export_error/missing_outputs`，其余安全产物继续导出。产物沿用原归属/路径安全检查，不依赖当前节点注册表解释历史下载。大文件打包使用临时文件并清理，不将全部音频或 ZIP 读入内存；正常下载、断开连接和发送失败均清理临时包。

新增批次对象使用显式持久化 schema `1.0`，只接受相同版本。旧项目/源文件没有 origin 时仍可读取，旧图 `{}` 输入继续表示运行音频，显式音频绑定和单文件启动语义不变。旧项目和运行不迁移、不补写，不用最新图或新节点结果反推历史。源元数据当前没有修改 API；未来若允许修改，需要先定义每次运行的源元数据快照语义。

单 JSON 清单在每次状态变化时原子更新，累计写入随清单增大存在写放大；历史分页仍需扫描批次记录，但不会为返回一页逐项加载全部子运行和项目。10000 是请求硬上限，不是大型目录的性能承诺。后续扩展应先评估分项状态文件与分页索引，不改变冻结快照、幂等或忙碌预留语义。首版本机通过 23 份音频、两个目录与分页浏览器场景；Linux 未在本轮实测。
