# 本地 ASR 能力发现与静态白名单问题

> 状态：Deferred（2026-10-29）。用户决定优先实现云端 ASR，暂缓本地 ASR 的进一步开发及本问题修复。现有 Mock/CrispASR 功能保留，不删除、不禁用、不回退已完成实现。

## 已确认的问题

当前限制的是识别后端标识，而不是具体模型文件名；模型文件已经支持从本地目录动态扫描。

- `backend/app/domain/pipeline_config.py` 的 `SUPPORTED_ASR_BACKENDS` 与 `backend/app/providers/crispasr.py` 的 `SUPPORTED_BACKENDS` 各自维护相同的固定后端白名单。
- `backend/app/application/local_asr_models.py` 已通过 `--list-backends-json` 查询当前 CrispASR 能力，但 `compiled_backends()` 又与静态白名单取交集。
- 节点配置校验和 Provider 执行继续使用固定白名单；前端 `AsrConfigFields.vue` 及工作流配置校验也维护已知后端集合。
- 结果：更新 CrispASR 后，即使新后端兼容现有调用协议，也可能被应用过滤或拒绝；多处名单存在同步遗漏风险。

这是已知的扩展性限制，不代表本机 CLI 支持的所有后端都已经过 VoiceTransl 验证。现有模型发现、参数安全和运行结果校验继续有效。

## 恢复处理时的方向

- 由服务端统一查询并校验当前 CLI 的能力列表，区分“实际支持”与“应用验证过”，避免多份静态白名单成为能力上限。
- 领域层检查配置结构和标识符安全，应用层结合本机能力检查运行可用性；不能通过取消安全校验来支持未知后端。
- 前端使用服务端能力数据，友好名称映射不应充当能力白名单；查询失败时明确提示，不能伪装为检查成功。
- 模型与后端只在匹配规则可靠时自动关联；协议不兼容的新后端仍需显式适配，不能声称所有新后端自动可用。
- 保持旧项目、已保存图及运行历史可读；运行中及已排队任务不得被后续能力或设置变化悄悄改写。

## 后续验收方向

1. 兼容现有 CLI 协议的新后端可被发现、选择并执行，不需要同步修改多份名单。
2. 非法标识符、能力查询失败和不受当前 CLI 支持的配置有明确错误，不静默回退 Mock。
3. 模型匹配不确定时不自动猜测；旧配置、历史、排队快照及安全边界回归通过。

云端 ASR 首个里程碑验收后，或用户明确重新调整优先级时，再细化本规格并决定是否恢复实施。本记录不授权立即重构本地实现。
